# Pyodide service roadmap

Open and deferred work, and the findings of the audit pass that are recorded rather than fixed.

## Closed by the audit pass

Recorded because the service is driven by the viewer's EEG analysis tools, so most of these were reachable from a user action.

- **A refused commission rejected the promise every caller reads as a result.** `runCode`, `runScript`, `loadPackages`, `setInputMutex` and `setupWorker` all awaited a commission the worker can refuse, and the service rejected it. The call sites — the power spectrum tool and the source localisation tool in the interface, and the builder's own registrar — are written to the declared contract, `if (!result.success)`, with no rejection handler anywhere: a refusal arrived as an unhandled rejection, the tool reported nothing, and `lastError` stayed empty. Each of them now resolves the failure with its cause.
- **A script that failed was recorded as loaded.** `runScript` wrote `'loaded'` and notified its waiters with `true` whatever the run returned, so every dependent went on to call definitions the interpreter did not have. A script whose run rejected was worse: it was left at `'loading'` with its waiters never notified, and from then on every `runScript` and every dependency wait for that name returned a promise that could not settle.
- **A dependency that had finished loading was read as one that had failed.** `awaitDependencies` waited on every name it was given as soon as any one of them was still loading, and waiting on an action that has already completed resolves `undefined`, which the check read as a failure. Two dependencies with one loaded and one loading refused the run.
- **The worker refused the `shutdown` commission until the interpreter had loaded.** The initialisation gate covered every action but setup, and `GenericService.shutdown` terminates its worker only once that commission comes back successful. So a shutdown that arrived while the runtime was still loading was refused, and after a load that failed every shutdown was refused for good — in both cases leaving the thread, and whatever it had allocated, for the life of the page.
- **Three actions never released their settled commissions.** `handleWorkerResponse` intercepts `run-code`, `load-packages` and `setup-input-mutex` before the base class sees them, and the base class is what drops the map entry; nothing dropped these, so the service kept a resolve and reject closure for every commission it had ever sent. Under the Python biosignal path that is one per viewport.
- **A run that raised left its arguments on the global scope.** The bridge binds a commission's parameters as globals for the duration of the call and released them only on the way out through the success path; the simulated `document` and `window` were never released on that path either. Both are now released in a `finally`, which is the path that matters: code that raises is also the code that leaves the largest arrays behind.
- **The main-thread runner never released them at all.** It binds onto the window, where a leftover name also shadows the window property that shares it.
- **A commission to load no packages was accepted.** The service filtered out the packages it had already loaded and commissioned the worker with whatever was left, including nothing; the worker's own check rejected a missing array but not an empty one, and reported success for having loaded nothing.
- **Two actions bypassed the guard that answers a throwing handler.** `setup-worker`, and the montage branch of it, are routed before the base class dispatcher, whose `try` is what reports a handler that raises. A `setup-montage` whose channel map the mapper rejects — a valid commission, refused deeper in — answered nothing at all, and the caller waited for the rest of the session.
- **A validation failure was posted to the default channel.** The worker layer called `validateCommissionProps` directly rather than through the base class wrapper, which leaves the reply on the global `postMessage`: correct on a worker thread, and the window wherever a base class redirects its transport, where it settles nothing.
- **`biosignal_filter_signal` built the lowpass and the notch filter from the highpass parameters.** Three copy-pasted sites. With a lowpass and no highpass it raised `'NoneType' object is not subscriptable`; with all three set the notch was built around 0.5 Hz, which makes the band `[-0.5, 1.5]` and scipy refuses the whole call — so the function could not succeed with anything but a highpass alone. Nothing in this repository calls it, which is why it had never shown.
- **A failure reason was posted as an error object in a field declared a string**, where it reads as `[object Object]` wherever a consumer interpolates it.
- **The ambient declarations were broken, and `skipLibCheck` hid it.** `RunPythonCode` — the type the montage processor takes its interpreter handle as — referred to a `RunCodeResult` that does not resolve in a global script, so every call through it was unchecked; the emitted declaration then named `RunPythonCode` with nothing to resolve it to, which left the processor unusable from typed code. The type is now declared and published with the others, and the ambient file holds the two Vite import forms and nothing else.
- **The lint configuration was the ESLint 8 format** that ESLint 9 does not read. The family rule set reported 87 problems, most of them one cause: the interpreter was reached through `(self as any).pyodide` at every site, which defeats type checking for everything the bridge returns. It is now one typed declaration of the worker scope.
- **The declared core range was `^1.0.0`** while the package type-checks clean against the 2.0.0 in the workspace, and the committed lockfile resolved core `0.3.0-2` from the registry — which is what a standalone clone would have installed whatever the range said. The range now says `^2.0.0`, with one caveat recorded in the builder's roadmap rather than here: the worker layer validates through the base class method `_validate`, which the *published* 2.0.0 does not have, so this package belongs with the six others whose range has to move to `^2.1.0` once core releases it. Its test suite needs the same core, because the loopback overrides `_postMessage` and `_close`.
- **There were no tests**, and the `test` script failed the family sweep with "No test files found".
- **A `.env.example`** declaring two variables that no file in the repository reads.

## What no test covers

The suite drives both halves of the service against each other — the real worker class, with only the interpreter replaced — so what is left out is what needs something a test environment does not have.

**The montage derivation.** [PyodideMontageProcessor](src/components/PyodideMontageProcessor.ts) reads its input through a shared memory mutex and computes in Python; the tests cover its montage registry, its filter translation and its refusals, and nothing of `calculateSignalsForPart`. That function is also the one place this package duplicates arithmetic from core's own montage processor — the interruption index bookkeeping in particular — so the two can drift apart silently. A fixture that builds a mutex-backed cache would cover both halves of that risk.

**The Python.** [biosignal.py](src/scripts/biosignal.py) has no runner here, and adding one means putting Python, numpy and scipy into the toolchain of a package published to npm. The filter fix above was demonstrated against numpy and scipy outside the package rather than asserted from reading, but nothing in the repository re-checks it. What is testable anywhere those two are installed is the arithmetic: the filter parameters, and the interruption indices that `_biosignal_insert_gaps` and `_biosignal_remove_gaps` have to agree on. The stronger test is the one that compares a derivation through this script against the same derivation through core's JavaScript path, and that needs both runtimes in one harness, which is a question of where such a harness belongs rather than of whether the script can be tested at all.

**The runtime load.** `loadPyodideRuntime` ends in a dynamic `import()` of a URL under the configured distribution folder, which no test environment serves, so the strategy it selects from `indexURL` is covered by nothing but the documentation.

## PyodideRunner is published and unwired

Nothing selects it: no registrar, setup or profile names it, and it cannot serve the biosignal path — it has no `setInputMutex`, and `setupBiosignalRecording` answers "Not yet implemented". It also carries two file-system experiments, `runWithReadAccess` and `runWithReadWriteAccess`, which open a directory picker, log the handle and ignore the script they were given.

It is a public export, so dropping it is a breaking change and keeping it is a promise. The question to settle is which: a context that cannot start a worker is a real case, but an untested variant that silently cannot do the one thing the service is mostly used for is not a fallback.

Its bindings are also riskier than the worker's by nature. A parameter is bound onto the window for the duration of a call, and a window property is load-bearing in a way a worker global is not — a parameter named `location` or `top` shadows the real one while the call runs. The names are the application's own rather than anything read out of a file, so the hazard is a typo rather than input. The runner keeps its interpreter in a field rather than on the window, so unlike the worker it has no name of its own to protect, and a list of the window's own would be guesswork about what a consumer's page needs.

## Most of the biosignal script has no caller

Nine of its entry points are called from nowhere in this repository or in the viewer interface: `biosignal_add_montage`, `biosignal_set_montage`, `biosignal_set_montage_filters`, `biosignal_set_filter`, `biosignal_set_output`, `biosignal_refresh_channels`, `set_series_canvas`, `biosignal_set_topomap_canvas` and `biosignal_filter_signal`. A consumer's own script can call any of them, which is what makes them a published surface rather than dead code — but nothing exercises them, and two could not have worked: `biosignal_filter_signal` until this pass, and `biosignal_set_montage_filters`, which reads a `filters` key off channels whose documented shape has none. The montage registry three of them are built around is marked not-yet-implemented in the script's own docstring.

They are not free either way. Every script this service loads shares one interpreter and one global namespace, so each name here is a name a consumer's script cannot use — and `set_series_canvas` is the one function without the `biosignal_` prefix that makes the rest of them collision-resistant.

## The template worker answers no shutdown

[PyodideWorker](src/workers/PyodideWorker.ts) composes the Pyodide layer onto core's `BaseWorker`, which registers no `shutdown` handler, so a service driving it would never terminate it. It is a reference implementation — unreachable through the package's exports and constructed by nothing — and the fix belongs in core's base class, where the same gap affects every worker built on it.

## A commission in flight when the service shuts down never settles

`GenericService.shutdown` clears the commission map once the worker has answered, and clearing it drops the resolve and reject closures without calling either. A `runCode` awaiting a reply when the viewer closes the resource therefore waits for the life of the page — the one way left for a caller of this service to wait forever, now that every refusal is reported. Core has the machinery for it: `_rejectAllCommissions` is what the worker-error paths use, and the shutdown path could do the same. The fix belongs there rather than here, because every service inherits the same clear.

## Smaller things

- **An unknown dependency is treated as satisfied.** `runCode(code, params, ['psd'])` runs whether or not `psd` has ever been loaded, because nothing here knows which scripts exist. The alternative — refusing every run whose dependency is managed elsewhere — is worse, but the consequence is that a missing dependency surfaces as a `NameError` from Python rather than as a refusal. The interface's source localisation declares `['biosignal']` and uses nothing from it, which is the same looseness from the other side.
- **The filter dictionary holds two kinds of thing.** `_biosignal['filters']` carries the three filter settings and the two default orders (`N_pass`, `N_stop`) in one dictionary, so a filter type has to be checked against a list rather than against the dictionary's own keys.
- **`umd/assets/` holds two worker bundles from an earlier toolchain.** The worker build cannot empty its output directory — the two builds write into the same one — so nothing removes them. They are not published, because `files` names `umd/*.js` and that pattern does not reach a subdirectory.
- **The service's `postMessage` has no reply path.** It posts a message with no request number and no commission, so a worker that answers it is answering nobody. Nothing calls it.
